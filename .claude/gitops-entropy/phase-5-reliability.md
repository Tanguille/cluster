# Phase 5: Reliability & Observability
**Completed:** 2026-08-06

## Findings

### Reliability
- Only 3 PDBs exist repo-wide: `searxng` (min1/2 replicas), `cloudflared` (min1/2), `dragonfly` (maxUnavail1/3). All are satisfiable — no PDB blocks a node drain today.
- The apps that would actually hurt during a rolling Talos node reboot — **coredns** (`kubernetes/apps/kube-system/coredns/app/helmrelease.yaml:14`, replicaCount 2), **k8s-gateway** (`kubernetes/apps/network/k8s-gateway/app/helmrelease.yaml:12`, replicaCount 2), and **envoy-gateway** (`kubernetes/apps/network/envoy-gateway/app/helmrelease.yaml:12-14`, replicas 2) — have no PDB and no topologySpread/anti-affinity. Nothing stops both replicas of any of these landing on the same node; a reboot of that node then drops cluster DNS or the ingress gateway. Given the known `DoNotSchedule` deadlock history, a `ScheduleAnyway` topologySpreadConstraint (not a PDB, which wouldn't help since there's no anti-affinity to protect) is the safer fix here.
- coredns has a hard `nodeAffinity` to `node-role.kubernetes.io/control-plane` (`helmrelease.yaml:62-68`) — fine, since all 3 nodes are control-plane+worker, this doesn't create a SPOF.
- No StatefulSets exist in the repo (dragonfly and cloudnative-pg use their own operators/CRDs, not raw StatefulSets) — N/A for that check.
- CronJobs: only 2 in scope. `qwen36-27b-hicache-prune` (`kubernetes/apps/ai/llmkube/models/qwen36-27b-sglang.yaml:29-75`) is fully correct: `concurrencyPolicy: Forbid`, both history limits, `backoffLimit: 2`, resource requests/limits set. `nextcloud-cron` (`kubernetes/apps/default/nextcloud/app/helmrelease.yaml:439-467`) sets history limits and resources but leaves `schedule`/`concurrencyPolicy`/`backoffLimit` to the upstream nextcloud chart's own defaults (not overridden here) — not flagged, chart defaults (`*/5 * * * *`, Forbid) are sane, but worth a spot-check if the chart is ever bumped.
- `qwen36-27b` InferenceService is hard-pinned to `control-1` via `nodeSelector` (`qwen36-27b-sglang.yaml` InferenceService spec) — this is the only node with the dGPU, so it's a hardware constraint, not a scheduling mistake. Not actionable.
- `Recreate` strategy on grafana (`kubernetes/apps/observability/grafana/instance/grafana.yaml:38-39`) and obico (`kubernetes/apps/default/obico/app/helmrelease.yaml:17`): both single-replica with RWO storage — correct pattern, no fix needed.
- No `maxUnavailable: 0` + `maxSurge: 0` combinations found anywhere.
- **Storage/backup gap**: kopiur backup coverage is opt-in per-app via a Kustomize component (`components/kopiur`) added to each app's `ks.yaml` — not an annotation. `immich-server`'s `ks.yaml` (`kubernetes/apps/default/immich/ks.yaml:1-13`) only includes `components/nfs-scaler`, **not** `components/kopiur`. The `immich-upload` PVC (`kubernetes/apps/default/immich/server/pvc.yaml`, ceph-filesystem, 100Gi — thumbnails, face-detection data, sidecar metadata, all real app state, not re-derivable from the library) has **zero backup coverage**. This is the one concrete backup gap found; correcting an earlier assumption, Hermes's PVC **is** covered (`kubernetes/apps/ai/hermes/ks.yaml` includes the kopiur component).
- No `storageClassName` gaps: every PVC/persistence block sets one explicitly.
- No RWO node-mobility risk: the only OpenEBS hostpath (node-local) volumes are the llmkube model/compile caches, and their consuming pods are already hard-pinned to the same node via `nodeSelector` for GPU reasons, so there's no anti-affinity/spread interaction that could strand a pod off its volume.
- Flux: cluster-wide default `timeout: 5m` / `retryInterval: 2m` is patched onto every child Kustomization (`kubernetes/flux/cluster/ks.yaml:38-40`). No AI/model workload overrides this. `llmkube-models` (`kubernetes/apps/ai/llmkube/ks.yaml:29-61`) health-checks `InferenceService qwen36-27b` reaching `Ready`, which on a cold model load can take several minutes — comfortably past the 5m default. Not fatal (2m retryInterval keeps retrying and `litellm`/`memini` depend only on the gated ks converging eventually) but produces a real reconcile-timeout/noisy-status window on every redeploy or node move of the GPU workload. Consider a longer `timeout` on `llmkube-models` specifically.

### Observability
- **Log aggregation exists and is wired up** — VictoriaLogs server + `victoria-logs-collector` (`kubernetes/apps/observability/victoria-logs/{app,collector}/helmrelease.yaml`), 14d retention, Grafana-operator dashboard integration. This contradicts a naive Loki/Vector/Alloy-name grep; there is no "no logging" gap.
- **PrometheusRule inventory**: 17 files covering coredns, node-problem-detector, cert-manager, flux, cilium, external-dns, drm-exporter, hermes, gatus, node-exporter, crowdsec (x2), cloudnative-pg, xmrig-guard, toolhive, rook-ceph, kopiur.
- **Flux reconciliation failure alerting exists**: `FluxInstanceAbsent`/`NotReady`, `HelmReleaseReconciliationFailure`, `KustomizationReconciliationFailure` (`kubernetes/apps/flux-system/flux-instance/app/prometheusrule.yaml`) — all `for: 5m`/`15m`, `severity: critical`. Good coverage, no gap.
- **Backup failure alerting exists and is thorough**: `kubernetes/apps/kopiur-system/kopiur/app/prometheusrule.yaml` has `KopiurBackupOverdue` (6h), `KopiurBackupCritical` (24h), `KopiurPolicyMetricsAbsent` (catches the exact July CRD-deletion failure mode where policies silently stop reporting instead of failing), `KopiurRepoEmpty`, `KopiurControllerNotLeader`. This is the strongest rule file in the repo — no gap.
- **Cert expiry**: no explicit "expires in N days" alert, but `CertManagerCertNotReady` (`kubernetes/apps/cert-manager/cert-manager/app/prometheusrule.yaml`) fires on renewal failure, which is the symptom that actually matters (cert-manager renews well before hard expiry; a stuck renewal is the real risk). Acceptable as-is.
- **Node NotReady**: no `KubeNodeNotReady`-style alert found anywhere in scope. This is a real gap — combined with the known "vmagent+vmalert go Pending on n-1 node memory" blackout, a node going down produces no in-cluster Prometheus-alerted signal for the node state itself.
- **Alerting-stack-down (the vmagent/vmalert blackout) has no dead-man's-switch**: no PrometheusRule exists for `victoria-metrics`/vmagent/vmalert self-health, and by construction a rule evaluated by vmalert can't alert on vmalert's own absence. The one mitigation in place is Gatus (`kubernetes/apps/observability/gatus/app/resources/config.yaml`), which pushes Discord webhooks **directly**, independent of the VM alerting pipeline — but Gatus has no endpoint checking vmagent/vmalert/vmsingle themselves, and Gatus runs in the same cluster, so the same node-memory-pressure event that produces the blackout can also evict Gatus. There is no external (off-cluster) heartbeat. This is the single highest-value gap to close, and it's the exact incident already logged in memory (`project_hypervisor_outage_monitoring_blindspot`).
- **Alert quality is good**: only 3 alerts lack `for:` (`HermesCronExporterAbsent`, `NodeKernelProblemEvents`, `NodeRebooted`) and all three are deliberately edge-triggered/self-bounding (absence-over-window, increase-over-window, boot-time-under-threshold) with a comment explaining why `for:` doesn't apply — not flappy in practice. Every alert has a `severity` label. No `runbook_url` or `description` annotations anywhere (only `summary`) — cosmetic, not urgent given the file-level comments already carry that context.
- `timestamp(a or b)` fake-freshness anti-pattern: not found. The only `timestamp()` usage (`xmrig-guard` PrometheusRule) is a plain single-series freshness check, correctly written, matching the already-fixed pattern from the memory note.
- **ServiceMonitor/PodMonitor coverage**: only 4 ServiceMonitors + 3 PodMonitors in scope. Given most exporters are wired via HelmRelease `serviceMonitor.enabled: true` (rendered separately, not hand-authored), this count alone doesn't indicate a gap — spot-checked storage (rook-ceph), network (cilium, envoy-gateway), and GPU (drm-exporter, kepler) all have their own PrometheusRule + are chart-rendered ServiceMonitors, so infra-critical scrape coverage looks intact. Did not exhaustively verify every media app (correctly out of scope per instructions).
- **Dashboards**: 30 `GrafanaDashboard` CRs, almost all thin wrappers around grafana-operator/community dashboard IDs rather than hand-authored inline JSON — stale-metric risk is low and owned upstream. Did not line-by-line audit all 30 given the volume/return tradeoff; flag for future manual spot-check only if a specific dashboard is reported broken.
