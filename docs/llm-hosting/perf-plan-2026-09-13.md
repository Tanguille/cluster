# qwen38-27b-vllm performance plan (2026-09-13)

Single R9700 (gfx1201), Qwen3.8-27B W4A16, upstream nightly pinned by digest
(`960228cf`, built 2026-09-12), AITER attention, fp8_e4m3 KV, CPU+NVMe KV offload,
`parallelSlots: 5`, `maxModelLen: 246944`.

## Decisions taken today

| Option | Verdict | Why |
|---|---|---|
| Fork vllm-radiance, rebase onto latest vLLM | No | Not a vLLM fork: ~50 single-anchor string patches on pinned v0.28.0 (`_patchlib.apply` aborts on anchor drift) plus custom torch/triton/aiter pins plus libr4d HIP kernels from a separate single maintainer. Their own 0.27.1 -> 0.28.0 bump was a dedicated branch. |
| Cherry-pick the R4D attention kernel | No | `radiance_r4d_attn.py` header, their measurement: +4.1% e2e prefill at 16K, +14.6% at 64K, decode unchanged. At 81.5% prefix hit that is ~0.25 s/request. |
| Adopt MXFP4 W4A8 as-is | No | Measured 09-09 (radiance 1.0.16, spec off, n=7): PP 2.13x-2.24x, TG 0.62x (20.10 vs 32.27 tok/s). Net ~20 s slower per request. TG number never band-classified. |
| Spec decode (MTP/DFlash) | No | Output-equivalence gate fails on this model (8/10 drafts not in target top-5); GDN verify collapses at depth; spec x xgrammar tool grammar = 100x. See `spec-decode-rejected.md`. |
| fp8 KV | Already on | Production runs `--kv-cache-dtype fp8_e4m3` (verified in the ReplicaSet args); the earlier "bf16 KV" premise was wrong. Nothing to do. |

Where radiance's 2x prefill actually comes from: the checkpoint format. MXFP4
weights with per-token fp8 activations run a hand-written fp8-WMMA HIP GEMM
(`radiance_mxfp4_fp8.hip`; their register-resident numbers: fp8 WMMA 325 TFLOP/s
vs f16 160). Our W4A16 prefill is upstream's Triton fused-dequant **bf16** GEMM
(`rdna_hybrid_w4a16.py`: "Triton for prefill, HIP skinny for decode"). That GEMM
cannot be moved onto a W4A16 checkpoint.

### Revised ranking under real load

1. **Queue, 28.8 s mean, p90 100 s.** Slots are saturated (avg 3.8/5 running,
   1.55 waiting). This is capacity, not kernel speed. Levers: the slot-count A/B
   (5 vs 6 vs 8, matched cudagraph capture sizes, KV usage is 73% so there is
   room) and anything that raises aggregate decode.
2. **KV lookup stall, ~6.4 s/request amortised, single events over 10 s.** Sits
   inside queue time. Same lever as the memory note: the lookup thread, not disk.
3. **Decode, 63.8 s mean** but that is 877 tokens at 4-way sharing; per-stream
   14 tok/s is the expected fast-band conc-4 number. Single-stream levers
   (`lm_head`, MXFP4 decode parity) still apply proportionally.
4. **Prefill, 7.0 s.** MXFP4's 2x would save ~3.5 s here.

The band gate (#1 in the plan) stays first because a slow draw halves
everything above at once; it just was not the problem in this 75-minute window.

Why #1 is the flags and not a smaller batch: a lower global
`max_num_batched_tokens` punishes the 38% of requests with <=1K computed
prefill that finish in one step. `long_prefill_token_threshold` chunks only
the prompts above it and leaves step budget for everyone else. Priority
scheduling reorders admission; it cannot preempt a running prefill. GPU
work is conserved: a 45K miss still costs ~37 s of GPU, the flags decide
who pays. 256-token chunks would give decode ~3 tok/s during a miss but
the Triton GEMM loses enough efficiency that total GPU time grows; 1024 is
the compromise, 2048 the fallback.

### #2 result: what effort actually reaches vLLM (2026-09-13, zero prod load)

Method: litellm v1.100.1 (the deployed version) run locally via `uvx` with
the production alias params against a mock backend that logs every request
body (`bench/litellm_mock_backend.py`, `bench/litellm_effort_replay.py`).
Plus vLLM source: `responses/protocol.py` builds
`chat_template_kwargs = merge_kwargs(request.chat_template_kwargs,
{reasoning_effort: reasoning.effort, ...})`, and `merge_kwargs` lets the
override win unless it is None.

| Client request | What vLLM `/v1/responses` receives | Effective effort |
|---|---|---|
| `/v1/messages`, no `thinking` | `chat_template_kwargs.reasoning_effort=medium` | medium (alias default) |
| `thinking: adaptive` (Claude Code) | alias kwargs + `reasoning.effort=medium` | medium |
| `thinking: adaptive` + `output_config.effort=medium` | same | medium |
| `thinking: enabled, budget 1024` | `reasoning.effort=low` | low |
| `thinking: enabled, budget 8000` | `reasoning.effort=high` | **400: template only knows xhigh/medium/low** |
| `thinking: disabled` | alias kwargs only | medium (litellm drops the disable) |
| `qwen-3.8-fast` | `enable_thinking=false` | no thinking |

So the Claude Code path already runs at **medium**; the 55% reasoning share
is at medium, not at the template's xhigh default. Two live confirmations:
prod logs have zero "Unexpected reasoning effort" rejections outside my
probe, and the chat path measured identical reasoning tokens via litellm
and direct at medium.

Consequences for the lever:

- There is no token budget knob: the Qwen3.8 template exposes only
  xhigh/medium/low and vLLM has no thinking-budget cutoff for it. The only
  step down is **low**, selectable per client (Claude Code `effortLevel`,
  or a litellm alias default).
- Whether low materially cuts reasoning on agent-shaped prompts is
  unmeasured. My 4-effort probe on a trivial prompt (low 147, medium 134,
  xhigh 76 reasoning tokens) is noise, and the realistic probe was killed
  after 25 min because prod is saturated by the very sessions it would
  measure. Run it at a quiet hour: 5 agent-style prompts x {low, medium},
  n=3 each, greedy, compare reasoning tokens and `toolcheck.py` 12/12.
- Any client sending `budget_tokens` above litellm's medium cutoff gets a
  400 from vLLM, silently to the user. Not happening in prod today.
- The 8/80min `ProxyModelNotFoundError` for `claude-opus-4-7` /
  `claude-sonnet-4-6` come from the Claude Code path (10.42.0.129, envoy
  internal). They cost no GPU. Fix if wanted: two extra `LiteLLMModel` CRs
  with those names on the qwen-3.8 backend (never `model_group_alias`).

### #4a result: MXFP4 decode kernel vs W4A16, same process (2026-09-13 16:30-16:50Z)

`bench/mxbench/mxfp4_vs_w4a16.py` run inside the serving pod (its vLLM,
its LDS-gate patch at 39321, its torch 2.12): radiance's
`radiance_mxfp4_fp8.hip` compiled with hipcc for gfx1201 (`build.sh`), both
kernels timed interleaved in one HIP process on random weights of the exact
decode shapes of Qwen3.8-27B. Prod was saturated (run=5) throughout, so the
table quotes the min over 4 interleaved blocks of 30; medians are in the raw
outputs (`run3.out`, `run_wperm0_final.out`). Four runs, same picture.

W4A16 = upstream `_rdna_hybrid_w4a16_apply_impl` (skinny `wvSplitK_int4_g`
while `K*M <= 39321`, else Triton). MXFP4 = per-token fp8 quant +
`radiance_mxfp4_fp8.launch`, `RADIANCE_MXFP4_WPERM=0`, `DECODE_NT=0` (their
qualified WPERM=1/NT=1 measured worse on every shape here).

| shape (N x K) | M=1 | M=2 | M=3 | M=4 | M=5 | note |
|---|---:|---:|---:|---:|---:|---|
| gdn in_proj 16384x5120 | 0.93-1.44x | 1.28-1.40x | 0.99-1.29x | 1.07-1.15x | 1.09-1.10x | |
| out_proj 5120x6144 | 0.73-1.02x | 0.98-1.07x | 1.09-1.30x | 0.89-1.02x | 1.14-1.25x | |
| **mlp gate_up 34816x5120** | **0.39x** | 0.36x | 0.40x | 0.41x | 0.43x | N > `DEC_MAX_N` 32768: not the decode kernel |
| mlp gate half 17408x5120 | 1.48x | 1.07x | 1.12x | 1.19x | 1.19x | what two launches would cost |
| mlp down 5120x17408 | 1.05-1.27x | 1.21-1.52x | **2.6-4.4x** | **2.7-4.3x** | **2.6-4.3x** | W4A16 leaves skinny at M=3 (K*M > LDS gate), Triton at ~150 GB/s |
| attn qkv 14336x5120 | 1.06-1.16x | 1.13-1.34x | 1.17-1.23x | 1.00-1.25x | 1.18-1.36x | |

Ratio = W4A16 time / MXFP4 time; >1 means MXFP4 faster. Effective weight
GB/s of the MXFP4 decode kernel 400-700, W4A16 skinny 350-540, W4A16 Triton
145-160.

Three conclusions:

1. **The production 0.62x is reproduced and attributed.** Summing the
   final run per decode step at M=1 (48 GDN layers + 16 attention layers):
   W4A16 29.9 ms, MXFP4 as shipped 43.9 ms = 0.68x (prod measured 0.62x). The
   whole loss is `gate_up`: 34816 rows exceed the decode kernel's
   `DEC_MAX_N=32768`, so on one GPU it silently takes the prefill-tiled
   kernel. On radiance's TP2 the fused N is 17408 and fits, which is why
   they never saw it.
2. **With gate_up split into two launches MXFP4 decode is faster than
   W4A16 at every M**: 1.12x at M=1 (26.8 vs 29.9 ms per step; 1.12-1.33x
   across runs) and **1.42x at M=4** (32.1 vs 45.7 ms; 1.4-2.0x across
   runs). Gate passes. The fix is a dispatch change in `radiance_mxfp4.py`
   (or `DEC_MAX_N` + scratch sizing in the .hip), not a kernel.
3. **Independent of MXFP4: W4A16 `down_proj` at M=3-5 is the single worst
   kernel in the decode step.** K=17408 x M >= 3 exceeds the skinny LDS
   gate and the Triton fallback runs at ~150 GB/s, a quarter of the memory
   ceiling. Prod runs at M=3.8 average. That one shape is 308 of 719 us of
   an M=4 GDN layer. A Triton config for (group 128, K 17408, N 5120,
   M <= 8), or a split-K skinny path, is a checkpoint-agnostic lever on the
   image we already run, and upstreamable.

Caveats: random weights (bandwidth kernels, values irrelevant); measured
under prod load with min-of-blocks, absolute numbers carry +-15% between
runs, ratios are stable in direction on every shape; the fp8 activation
quant is inside the MXFP4 timing; the W4A8 numerics question is separate and
was answered by the 09-09 GSM8K/tool gates (95.3 vs 92.0, 8/8).

### Decision after #4a (2026-09-13 18:35 CEST): W4A16 down_proj fix first, MXFP4 (#4b) deferred

Conclusion 3 is checkpoint-agnostic and fixable on the running image, so it
goes first. #4b is parked, not dropped. What it takes, so nobody has to
rediscover it:

#### #4b: MXFP4 W4A8 as a quant plugin on the upstream nightly

1. Kernel: `radiance_mxfp4_fp8.hip` from magiccodingman/vllm-radiance
   (Codeberg libr4d), built with `bench/mxbench/build.sh` (hipcc, gfx1201,
   pybind11). Already compiles and runs inside our image.
2. Dispatch fix: `radiance_mxfp4.py` routes N > `DEC_MAX_N` (32768) to the
   prefill-tiled kernel. Fused gate_up is N=34816 on one GPU. Either launch
   twice on the two 17408-row halves (bench shows 1.07-1.48x vs W4A16 per
   half) or raise `DEC_MAX_N` and size the split-K scratch
   (`set_decode_scratch`, `DEC_KS=4` x 64 x N fp32) in the .hip. Test both;
   the two-launch form needs no kernel change.
3. Env that won: `RADIANCE_MXFP4_WPERM=0`, `RADIANCE_MXFP4_DECODE_NT=0`,
   `RADIANCE_MXFP4_DECODE_MAX_M=64`. Their qualified WPERM=1/NT=1 lost on
   every shape on gfx1201 single-GPU.
4. Packaging: a `vllm.general_plugins` entry point calling
   `register_quantization_config("radiance_mxfp4")` with a
   `QuantizationConfig` + `LinearMethodBase` that owns the packed e2m1
   [N,K/2] uint8, e8m0 scales [K/32,N] uint8, per-row `wref = ws.max(0)`,
   and calls `ops.scaled_fp8_quant(x, use_per_token_if_dynamic=True)` +
   `rad.launch(...)`. lm_head and in_proj_a/b stay bf16. No vLLM source
   patches; ships as a ConfigMap-mounted package + the .so.
5. Checkpoint: the W4A8 MXFP4 conversion used on 09-09 (GSM8K 95.3 vs 92.0,
   tools 8/8 on radiance). Re-run both gates on the plugin.
6. Gate for cutover, band-classified (mem_busy >= 60 at run=1, sclk >= 3100
   before quoting): decode >= 0.97x prod at M=1 and M=4, prefill >= 1.8x at
   16K and 64K, tools 12/12. Expected from #4a: 1.12x@M=1, 1.42x@M=4 decode,
   ~2x prefill; the decode part shrinks by whatever the down_proj fix below
   recovers first, so re-baseline W4A16 after that lands.
7. Cost: one restart for the retest, one for the cutover. Pairs with the
   #1 + #5 bundle if timing allows.

### down_proj fix result (2026-09-13 18:40-19:10 CEST, in-pod, prod at run=5)

Sources and raw outputs in `bench/downfix/`. Two candidates measured in the
same process; timing under CUDA-graph replay (`final_graph.out`,
`triton_m32.out`) because a nice-19 process next to the engine is
CPU-starved and eager launch gaps punished multi-launch candidates (the
eager `sweep.out` "2.3x" for split-K was that artefact, not a result).

**Split-K over the HIP skinny kernel: rejected.** The kernel derives its
row stride from the activation's K, so chunks must be contiguous, so the
weight has to be stored as K-chunks and every M pays S launches:

| 5 | 266 | refused (K*N > 39321) | 1.27x |
| 64 (prefill tail) | 290 | 0.59x | 0.53x |
| 512 | 1320 | 0.71x | 0.69x |
| 4096 | 13820 | 1.19x | 1.19x |

M in {3,4,5,8,16,32} (`triton_m32.out`); `2 warps, 1 stage` wins 14/30

Shipped as a second patch in the existing `zz_lds_gate_impl.py` import hook
(replaces `triton_w4a16_skinny_fmt_gemm` for M <= 32 on gfx12x; same tile,
same reduction order, output bit-identical to the original on every shape
and M tested, `test_hook.py`). Expected step-level effect: at prod M=3-5
only down_proj is on Triton, 42 us x 64 layers = ~2.7 ms of a ~45 ms M=4
step (~6%); at M=6-32 every linear gets the ~1.2x. Honest size: single
digits on decode, zero on prefill. Needs a pod restart, so it rides
the #1 + #5 cutover rather than paying a cold-KV stall on its own. Upstream:
a one-line change to the gfx12x `M <= 32` branch plus this sweep.

headroom: the skinny kernel itself drops to 260-320 GB/s once K is chunked,
and no Triton tile got past ~230 GB/s at M <= 5 on this shape. Closing the
remaining gap on down_proj at M=3-5 needs a kernel (split-K inside the HIP
kernel, or MXFP4 #4b), not a config.
